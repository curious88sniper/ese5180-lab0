4. Kconfig
Companion Reading:
Zephyr RTOS Embedded C Programming: Using Embedded RTOS POSIX API by Andrew Eliasz
Chapter 4. Zephyr RTOS Multithreading
Kconfig is Zephyr's configuration system, enabling control over OS-level features, drivers, and application-specific settings. It uses a textual configuration language to define symbols (options) and their dependencies, allowing developers to tailor the Zephyr build to their specific hardware and software requirements. Kconfig controls the software configuration of a Zephyr project, whereas Device Tree handles the hardware configuration.
4.1 Kconfig Implementation Details
prj.conf File: This is the primary file where Kconfig settings for your application are typically stored. Each line represents a Kconfig symbol and its value.For example:
CONFIG_LOG=y: Enables the logging subsystem.
CONFIG_LOG_DEFAULT_LEVEL=3: Sets the default log level to 'info'.
Interactive Menu (menuconfig): While you can directly edit prj.conf, Zephyr provides an interactive menu-driven configuration tool. You can access it by running west build -t menuconfig in your project directory. This tool allows you to navigate through a hierarchical menu of all available Kconfig options, enabling or disabling features and setting their values. It also helps in understanding dependencies and conflicts between different options. 
Relationship between prj.conf and menuconfig:
prj.conf acts as an overlay or initial set of configurations. When you run west build, the Kconfig system processes prj.conf along with default configurations and board-specific settings.
menuconfig provides a visual and interactive way to view and modify these settings. Any changes made in menuconfig are typically saved back into your project's configuration files (often in a hidden .config file within the build directory), which then influence the subsequent builds.
Verification of Settings: After building your project, the Kconfig system generates a .config file in your build directory (e.g., build/zephyr/.config). This file contains the final resolved values for all Kconfig symbols, taking into account prj.conf, default settings, and any board-specific overrides. You can inspect this file to verify that the symbols defined in your prj.conf are correctly set and that there are no unexpected conflicts or omissions. This verification is crucial to ensure your application is built with the intended features and driver support.
Integration with Build System: Kconfig is tightly integrated with Zephyr's CMake-based build system. The Kconfig options determine which source files are compiled, which drivers are included, and how various subsystems are configured during the build process.

5. Device Tree (DT)
Companion Reading:
Zephyr RTOS Embedded C Programming: Using Embedded RTOS POSIX API by Andrew Eliasz
Chapter 9. Understanding and Working with the Device Tree in General and SPI and I2C in Particular
In Zephyr, DeviceTree (DT) is a hardware description system. Instead of hardcoding pins or drivers in C code, Zephyr uses .dts (DeviceTree Source) files that describe:
What hardware exists (GPIO controllers, UARTs, LEDs, sensors, etc.).
How it is wired (e.g., LED0 is on GPIO0 pin 13, active low).
Which devices should be enabled (status = "okay" vs "disabled").
At build time, Zephyr compiles .dts files + your app’s overlays (.overlay) into C macros. Drivers and your code use those macros to bind to devices without knowing low-level details.

6. Printing vs. Logging
Resources
CMake and Kconfig tricks for common code in Zephyr apps - The Golioth Developer BlogNordic Application DevelopmentDebugging Zephyr for Beginners: printk() and the Logging Subsystem - The Golioth Developer Blog
In this section, you will implement a simple sum function in two different ways: once using printk() and once using the Logger module. The active implementation will be selected at build time using Kconfig options (CONFIG_SUM_PRINT and CONFIG_SUM_LOG). This assignment will help you practice console output, explore the differences between printk and the Logger, and understand how Kconfig choices can control application behavior.
To print basic messages to the console, we’ll use the printk() function. Its syntax is very similar to the standard printf() in C: you can pass in a string literal or a format string along with variables you want to display. Unlike printf(), printk() is designed for embedded systems and supports only a simplified set of features, making it lightweight and efficient.
Enable console driversMake sure the console is enabled by setting CONFIG_CONSOLE in your application’s configuration file.
Choose a console backend Zephyr supports several backends, such as the UART console (CONFIG_UART_CONSOLE) and the RTT console (CONFIG_RTT_CONSOLE). For this lab, we’ll use the UART console, since its output can be easily viewed in a serial terminal (for example, the built-in terminal in VS Code). On most boards, UART is already set as the default.
6.1 Logging
While printk() is useful for simple output, the Logger module is the recommended way to send messages to the console. Unlike printk(), which blocks until every byte of the message has been sent, the Logger offers more efficient and flexible logging. It supports both in-place and deferred logging and comes with several advanced features, including:
Support for multiple backends
Compile-time filtering at the module level
Runtime filtering that can be set independently for each backend
Timestamping with a user-provided function
A dedicated API for dumping data
Optional colored output in logs
Integration with printk() (printk messages can be redirected through the Logger)
You can read the full list of features in the Logging documentation.
Logs can also be compiled in, but filtered at run time using a dedicated API. The run-time filtering is independent for each backend and each module. There are four severity levels available in the system that can filter the warnings appropriately.

A quick primer on how the test framework works in Zephyr:
Zephyr uses Board Simulation /Twister to run tests
